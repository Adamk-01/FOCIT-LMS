FOCIT LMS
Backend Architecture &Moodle Integration Guide
Implementation handoff for the backend development team
PurposeExplain the overall Node.js backend structure, the boundary between FOCIT and Moodle, the official course-registration workflow, data ownership, integration reliability, security responsibilities, and the implementation sequence.
Target stack: Node.js (TypeScript recommended), Express.js, PostgreSQL, Redis, a background worker, and Moodle Web Services.
Status: Proposed architecture for implementation. Endpoint names, exact Moodle functions, eligibility rules, and role permissions must be confirmed during development.
1. Executive summary
FOCIT LMS is a connected system with two distinct responsibilities. FOCIT is the academic and administrative control layer. Moodle is the learning delivery engine. The Node.js backend connects the two through a dedicated Moodle integration adapter.
Core ruleFOCIT is the source of truth for identity, academic structure, eligibility, and official course registration. Moodle is the source of truth for learning activities, course materials, quizzes, forums, submissions, and learning grades.
Build this initially as a modular monolith: one Node.js API codebase divided into clear modules, plus a separate worker process for background integration jobs. This is simpler to operate than microservices while leaving room to split modules later.

How a request should move through the code
HTTP route → authentication/authorization middleware → controller → service → repository → PostgreSQL
A controller should handle HTTP concerns and response formatting. The service enforces business rules. The repository owns database queries. The Moodle adapter owns Moodle API calls. Avoid placing SQL and Moodle calls directly in controllers.

6. Moodle integration adapter
All Moodle communication should go through src/integrations/moodle/. This isolates Moodle-specific function names, request parameters, response formats, timeouts and error handling from the rest of the application.
Adapter responsibilities
Read Moodle base URL and service credentials from environment/secret management; never expose them to React.
Make authenticated Moodle Web Services requests over HTTPS.
Resolve FOCIT user/course mappings before attempting enrolment or grade reads.
Translate Moodle responses into stable internal types so controllers do not depend on raw Moodle payloads.
Apply request timeouts, safe logging, error classification and retry rules.
Keep an allowlist of the Moodle functions the integration needs; enable only necessary capabilities for the service account.
Make writes idempotent where possible and record enough state to reconcile uncertain outcomes.
Moodle setup prerequisiteAn administrator must enable the appropriate Moodle Web Services protocol, create a restricted integration service account/token, and confirm the exact Moodle API functions available in the installed Moodle version. Do not assume every function is enabled by default.
7. Critical workflow: official registration → Moodle enrolment
This is the most important integration path because FOCIT must remain authoritative even when Moodle is temporarily unavailable.
Student authenticates and submits a registration request to FOCIT.
The API validates the student, offering, semester, prerequisites, registration window, unit limits and any approval requirements defined by the institution.
Within one PostgreSQL transaction, FOCIT writes the registration state and a durable outbox event. If either write fails, the transaction rolls back.
After commit, a worker picks up the outbox event. The API does not wait for Moodle to be available before preserving the official registration.
The worker resolves the student's Moodle user ID and the offering's Moodle course ID. Missing mappings are reported as actionable integration failures.
The worker invokes the appropriate Moodle enrolment function and confirms the result.
On success, the event is marked complete and the registration's Moodle sync status is updated. On a retryable error, the job is rescheduled with backoff. Permanent errors are surfaced for administrator action.
A reconciliation job periodically compares expected FOCIT registrations with Moodle enrolments and repairs or flags drift.
Example state model:FOCIT registration: draft → submitted → approved → withdrawn (policy-dependent)Moodle sync:         pending → processing → synced                                      └────→ retrying / failed
Important distinctionOfficial registration status and Moodle synchronization status are separate. A registration can be approved while Moodle sync is pending. The UI should communicate that state accurately rather than falsely claiming the student is already enrolled in Moodle.
8. Reliability: transactional outbox, retries and idempotency
Do not rely on an in-memory promise or a fire-and-forget request after saving a registration. A process crash could lose the Moodle enrolment action.
Write the registration change and outbox event in the same PostgreSQL transaction.
Give each event a stable ID and use safe deduplication/idempotency rules.
Retry transient network errors, timeouts, rate limits and temporary Moodle server errors with exponential backoff and jitter.
Do not endlessly retry invalid mappings, permission errors or malformed requests; mark them for operator review.
Track attempts, timestamps, last error and next retry time.
Make worker processing safe if a job is delivered more than once.
Provide admin visibility into pending, retrying and failed events.
Redis/BullMQ can distribute and schedule work, but the PostgreSQL outbox should remain the durable record that the integration action is required. If the queue is lost or Redis restarts, the worker must be able to republish pending outbox events.
9. Grade synchronization
Moodle Gradebook remains the source of truth for learning grades.
FOCIT reads only the grade data it is authorized to show and only for mapped courses and users.
Store sync metadata and, if required for dashboard performance, a clearly identified read model/cache—not a separate editable gradebook.
Record the Moodle source reference and last synchronization time so stale data can be detected.
Define policy for hidden grades, unpublished grades, missing grades, resits, overrides and grade changes before exposing results.
Use scheduled sync plus targeted refresh where appropriate; handle pagination, API limits and temporary failures.
Exact Moodle grade API functions and field mappings must be verified against the institution's Moodle version and permissions before implementation.

Authorization must combine role with resource scope. A lecturer role alone must not grant access to every course. Check course assignment, department/faculty ownership, student ownership and record status in the service layer or a centralized policy service.
12. Security and operations checklist
Validate environment variables at startup; commit only .env.example, never real credentials.
Use TLS/HTTPS in deployed environments and secure cookies or appropriately protected tokens.
Hash passwords with a current password-hashing algorithm if FOCIT manages passwords itself.
Use request validation, parameterized database access, rate limiting and centralized error handling.
Restrict CORS to known frontend origins in production.
Keep Moodle service tokens server-side and grant only the required Moodle capabilities.
Redact passwords, tokens, session IDs and sensitive student information from logs.
Record audit trails for approvals, withdrawals, role changes and course mapping changes.
Back up PostgreSQL and test restore procedures; monitor database, Redis, worker and Moodle availability.
Add health/readiness checks and alert on sustained outbox backlog or failed synchronization.
13. Testing and acceptance criteria
Test area
Minimum acceptance criteria
Academic rules
Ineligible students are rejected; valid students can register; duplicates are prevented.
Authorization
Users cannot access other students' records or courses outside their permitted scope.
Transaction/outbox
Registration and outbox event either both commit or both roll back.
Moodle unavailable
Official registration remains recorded; event is retried; UI shows sync pending/failed accurately.
Idempotency
Repeated worker delivery does not create duplicate enrolments or corrupt state.
Mapping errors
Missing Moodle user/course mappings produce visible actionable errors.
Grade sync
Only authorized, policy-visible grades are returned; sync timestamps and stale states are tracked.
Auditability
Approvals, withdrawals, mapping changes and admin actions are traceable.
Reconciliation
A test can detect a missing Moodle enrolment and repair or flag it.
14. Recommended implementation sequence
Bootstrap TypeScript/Express, configuration validation, logging, database connection, migrations, error handling and API docs.
Implement users, student profiles, role assignments, authentication and scope-aware authorization.
Implement the academic catalogue, offerings, semesters and lecturer assignments.
Implement registration eligibility, approval rules, transaction handling, audit records and outbox events.
Build the Moodle adapter and verify connectivity, user lookup/create strategy, course mappings and enrolment functions.
Build the worker, retry policy, integration status endpoints and reconciliation process.
Implement timetable, announcements and role-specific dashboard APIs.
Implement grade synchronization and learning links, then harden with end-to-end tests, backups and monitoring.
15. Decisions to confirm before coding
Exact Moodle version, base URL, Web Services protocol, enabled functions and service-account permissions.
Whether authentication is local to FOCIT or uses an institutional identity provider/SSO.
Official registration approval workflow and who may approve, amend or withdraw registrations.
Eligibility rules: prerequisites, carryovers, unit limits, registration windows and add/drop periods.
Whether one course offering maps to one Moodle course or whether multiple offerings share a Moodle course.
Grade visibility rules, sync frequency, handling of hidden/unpublished grades and official-result policy.
Course Representative permissions and the authoritative timetable/announcement publishing workflow.
Deployment environment, secret management, backup/restore ownership and monitoring/alert destinations.
16. Developer's definition of done
The integration is ready for an MVP release when:
FOCIT is the authoritative store for users, academic structure, eligibility and official registrations.
FOCIT IDs map reliably to Moodle user and course IDs; mapping changes are audited.
An approved registration creates a durable outbox event and results in Moodle enrolment after successful processing.
Moodle downtime does not lose approved registrations or silently lose integration work.
Retries, idempotency, failure visibility and reconciliation are tested.
Learning materials, quizzes, forums, submissions, question bank and Gradebook remain Moodle-owned.
Role and scope authorization, grade visibility, logging, migrations, tests and operational monitoring are in place.
